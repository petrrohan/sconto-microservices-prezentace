Motivace

Proč microservices pro Sconto?

Problémy monolitu

  • Každý deploy = nasazení celého Shopsys (risky)
  • Emaily, PDF, platby — vše svázané v jednom repozitáři
  • Selhání jedné funkce může shodit celý e-shop
  • Nové funkcionality musí čekat na celkový release
  • Frontend tým přetížený — tvořit UI pro každou funkci zvlášť je nereálné
Realita týmu: PHP vývojáři (celý tým), žádný DevOps, FE přetížení. Musíme zůstat v Symfony ekosystému.

Co nám microservices dají

  • Nezávislý deploy — nasadíme jen email service, nic jiného se nehne
  • Izolace selhání — pád PDF generátoru neovlivní e-shop
  • Škálovatelnost — platby můžeme škálovat nezávisle na zbytku
  • Rychlejší vývoj — každý service = vlastní repo, vlastní testy, vlastní CI/CD
  • ECS Fargate — jednodušší než Kubernetes, méně práce s údržbou
Klíčové rozhodnutí: ECS Fargate místo Kubernetes — tým nemá DevOps kapacitu na správu Kubernetes.

Proč Symfony 7.2?
Boilerplate je o generaci napřed oproti monolitu (Symfony 6.4 LTS). Microservices nemají závislost na Shopsys packages — můžeme jít na novější verzi.
Proč API Platform?
Entita + #[ApiResource] atribut = kompletní API (čtení, vytváření, editace, mazání). Automatická dokumentace, stránkování, filtrování — vše zabudované. Šetří 80% kódu oproti ručním controllerům.

Co je pro tým nové?

  • API Platform — tým nikdy nepoužíval, ale drasticky zrychlí vývoj API
  • ECS Fargate — místo Kubernetes (jednodušší, bez DevOps overhead)
  • AWS Cognito — autentizace bez PHP kódu (ALB řeší za nás)
  • SSM Parameter Store — bezpečné úložiště hesel a API klíčů

Co je ALB? Application Load Balancer = „rozdělovač provozu" od AWS. Přijde požadavek na /api/emails/send → ALB ho pošle na Email service. /api/pdf/generate → na PDF service. Jeden vstupní bod pro všechno.
Co je SSM Parameter Store? AWS trezor na hesla, API klíče a konfiguraci. Místo .env souborů v repozitáři — hesla bezpečně uložená v AWS, service si je načte při startu. Nikdy v kódu, nikdy v Gitu.
Úspora: 1 Aurora instance místo 4–5 = ~$150–400/měs. Sdílený ALB i Redis = $0 navíc. ECS Fargate = platíme jen za běžící tasky.
Izolace: Každý service = vlastní GitLab repo, vlastní ECR image, vlastní ECS task definition. Deploy jednoho nerozbije ostatní.
NOVÉ PRO TÝM

Autentizace

AWS Cognito — zero auth kód v PHP

Jak to funguje: ALB (rozdělovač provozu) ověří přihlášení automaticky. PHP microservice dostane info o přihlášeném uživateli v hlavičkách požadavku. Žádný přihlašovací kód v Symfony — vše řeší AWS.
Cena: $0 — Cognito je zdarma do 50 000 uživatelů/měsíc, admin tým = 5–20 lidí. Komunikace mezi aplikacemi (E-shop → microservice) se řeší API klíči v AWS trezoru.

Autorizace aplikací

Jak se E-shop, POS a IM připojí k microservices?

Každá aplikace se autorizuje vlastním API klíčem. Klíče bezpečně uložené v AWS — nikdy v kódu.

Jak to funguje: Každá aplikace má svůj unikátní API klíč. Posílá ho v hlavičce X-Api-Key při každém požadavku. Service ověří klíč a ví, kdo volá.
Kde jsou klíče: V AWS SSM Parameter Store — bezpečný trezor. Nikdy v kódu, nikdy v .env, nikdy v Gitu. Service si je načte při startu.
Oprávnění: Každý klíč má vlastní oprávnění — E-shop může volat emaily a PDF, POS jen platby. Oddělená hesla = pokud unikne jedno, ostatní jsou v bezpečí.

Co přesně se stane, když napíšete entitu?

PHP dev napíše TOTO:

// src/Entity/EmailNotification.php
#[ApiResource]
#[ORM\Entity]
class EmailNotification {
  #[ORM\Id, ORM\GeneratedValue]
  public ?int $id = null;

  #[ORM\Column]
  public string $to;

  #[ORM\Column]
  public string $subject;

  #[ORM\Column(type: 'text')]
  public string $body;

  #[ORM\Column]
  public string $status = 'pending';
}

Porovnání časů:

Bez API Platform: nový endpoint = Controller + DTO + Route + Serializer + dokumentace = 2–4 hodiny

S API Platform: nový endpoint = přidat property do entity = 5 minut
Kdy potřebujeme vlastní logiku?
API Platform podporuje State Processors — vlastní kód, který se spustí po POST/PUT. Např. po vytvoření emailu → odeslat přes Mailersend. Entita = data, Processor = logika.

Migrace

Nový systém — aplikace se připojují postupně

Neextrahujeme z monolitu. Stavíme vše od nuly jako nový, nezávislý systém. Aplikace (E-shop, POS, IM) se připojují, kdy chtějí.

FÁZE 1

Infrastruktura + UI

ECS cluster, ALB, Cognito, SSM secrets. Next.js Dashboard — společné admin UI jako vstupní bod.

FÁZE 2

Microservices naživo

Nová logika, nový kód. Emaily, PDF, platby — vše postavené od základu na Symfony 7.2 + API Platform.

FÁZE 3

Appky se připojují

E-shop, POS, IM — každá aplikace se připojí na API nezávisle, ve vlastním tempu. Žádné čekání.

FÁZE 4

Stará logika pryč

Až se appka připojí → stará duplicitní logika se smaže. Jedna pravda, jedno místo.

Klíčový princip: Neřešíme „jak to vytáhnout z monolitu". Stavíme nový systém vedle. Aplikace (E-shop, POS, IM) se připojují přes API postupně — žádná velká migrace, žádný velký třesk.
Výhoda: Každý tým (E-shop, POS) si řídí tempo připojení sám. Neblokují se navzájem. Microservice funguje i kdyby byl připojený jen E-shop a POS zatím ne.
KRITICKÝ BLOKÁTOR

VPC Peering — neexistuje!

E-shop, POS i IM musí vidět na microservices. Aktuálně žádné privátní spojení mezi VPC neexistuje.

Problém: E-shop (vpc-016) nemá privátní cestu k microservices (vpc-037). POS a IM jsou ve stejné VPC, ale peering s E-shopem chybí. Toto MUSÍ vyřešit Alef (externí DevOps).
Řešení: VPC Peering mezi vpc-016 ↔ vpc-037 (doporučené). Blokuje celou strategii — musí se vyřešit jako první!

Bezpečnostní pojistky

Co se stane, když něco selže?

Každý systém občas selže. Tyto pojistky zajistí, že selhání jedné části neshodí zbytek.

Selže nasazení nové verze?
AWS automaticky vrátí předchozí fungující verzi. Nový deploy proběhne jen když nová verze projde kontrolou „žije a odpovídá". Žádný ruční zásah.
Selže odeslání emailu přes Mailersend?
Email se automaticky zkusí odeslat znovu (3× s odstupem). Pokud i poté selže, uloží se do „fronty selhání" — neztratí se, opravíme a odešleme ručně.
Spadne databáze nebo Redis?
Každý microservice má kontrolní endpoint /health. AWS ho kontroluje každých 30 sekund. Pokud neodpovídá → automaticky restartuje service.
Externe služba (PDF.co, Erste) je nedostupná?
Požadavky jdou přes frontu na pozadí — uživatel nemusí čekat. Pokud služba neodpovídá, zkusíme to znovu automaticky. E-shop/POS mezitím fungují normálně.
Příliš mnoho požadavků najednou?
Omezovač rychlosti zajistí, že nepřekročíme limity externích služeb (např. Mailersend 1000 emailů/min). Požadavky nad limit se zařadí do fronty.
Klíčový princip: Nikdy nevoláme externí služby „přímo" (synchronně). Vždy přes frontu na pozadí = uživatel dostane rychlou odpověď, zpracování běží na pozadí.

Monitoring

Monitoring stack — již nakoupené nástroje

Sentry: Zachytí každou chybu v PHP kódu. Ukáže přesný řádek, stack trace, kdo byl přihlášený. Notifikace do Teams.
SpeedCurve: Monitoruje dostupnost (uptime). Kontroluje /health endpoint každých 30s. Pokud neodpovídá → Teams alert.
CloudWatch: AWS metriky — využití CPU, paměti, počet zpráv ve frontě. Alarmy při překročení limitů.
