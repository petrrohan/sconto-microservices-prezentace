Kde jsme dnes

IM 2.0 — Soucasny stav

Uz jsme usli kus cesty: IM 1.0 (monolit + MS SQL) → IM 2.0 = rozsekan na 4 samostatne nasaditelne casti + migrace z MS SQL na AWS Aurora (PostgreSQL). To je zaklad, na kterem stavime dal.

Co nas boli

4 zasadni problemy soucasneho IM

1
99 % pollu = prazdno
Crony bezej co 5 minut. Zeptaj se IM: "Zmenil se sklad?" Odpoved: "Ne." A to porad dokola. Tisice zbytecnych API callu denne. Zbytecna zatez na IM, na sit, na vsechno.
2
Latence 1–5 minut
Cena se zmeni v ERP. Zakaznik na e-shopu vidi starou cenu jeste 5 minut. Objedna za starou cenu. Reklamace. Drama. A to jenom proto, ze cron se spusti az za 5 minut.
3
Push selze = data pryc
IM nekam pushne data. Konzument nebezi (deploy, bug, cokoliv). Data zmizi. Zadna fronta, zadny retry, zadny dead-letter. Proste se to ztrati a nikdo se nic nedozvi.
4
Novy konzument = novy API projekt
Chce se pripojit novy system? Super. IM tym musi napsat novy API projekt, novy controller, novy autorizacni model. Tydny prace. Pokazde znova.
Vysledek: Tym IM travi cas budovanim novych API projektu pro kazdyho konzumenta, misto toho aby zlepsoval business logiku. Jde o strukturalni problem, ne o lidi.

Prvni krok

IM 3.0 — PG Replika + IM = SSOT

IM 3.0 resi odkud data prichazi. Konec CSV, konec jedine API trubky do ERP. IM cte primo z Azure PostgreSQL repliky.

Co se meni v IM 3.0
  • CSV z Moeve → Azure PG replika — zakaznici, firmy, produkty, sklady ctene primo z DB
  • Prepocty z e-shopu → do IM — ceny, dostupnost, dodaci lhuty. IM = Single Source of Truth
  • Moeve webservice bypass — necteme pres tu API trubku (3 roky na Windows!), cteme z PG repliky
  • E-shop + POS = stejna data — neni treba replikovat logiku e-shopu do POS
IM 3.0 resi: Cerstvost dat (near real-time misto 1x/den CSV). IM se stava SSOT — vsechny prepocty na jednom miste.
Co IM 3.0 NERESI
  • Crony bezej dal — konzumenti porad polluji IM co 5 min
  • Push = fire & forget — zadna fronta, zadny retry
  • Novy konzument = novy API projekt — stale manualni prace
  • 99% pollu = prazdno — zbytecna zatez zustava
Proto potrebujeme IM 4.0: PG replika resi DATA, ale ne DISTRIBUCI dat ke konzumentum. To vyresi az Apache Pulsar.

Druhy krok — IM 4.0

Apache Pulsar — reseni distribuce dat

IM 3.0 vyresi odkud data cteme. Ale jak je dostat ke konzumentum? Pulsar = Kafka + RabbitMQ + SQS v jednom. Open-source. Cloud-native.

01
Oddeleny compute + storage
Brokers (stateless) vs BookKeeper (storage). Chces vic throughputu? Pridej broker. Chces vic dat? Pridej bookie. Skalovani v sekundach, bez rebalancingu.
02
4 subscription typy
Exclusive, Failover, Shared, Key_Shared. Kazdy pattern, co potrebujes. Jeden konzument? Exclusive. Vic workeru? Shared. Ordering per key? Key_Shared.
03
Multi-tenancy
Tenant per system/tym. Namespace per domena. Uplna izolace bez extra infrastruktury. Sconto = jeden tenant, ruzne namespacy pro bridge, orders, stock...
04
.NET + PHP + Java + Go
DotPulsar = nativni C# klient. Symfony Messenger pro PHP. Plus Kafka protocol compatible (KoP) — existujici Kafka klienti se pripojej BEZ zmeny kodu.
05
Tiered Storage → S3
Starsi data automaticky do S3. Neomezena retence. Chces replay zprav z minuleho mesice? Zadny problem. A hlavne: levne.
06
Dead Letter + Retry
Built-in retry topic + DLQ. Zprava se nepodarila zpracovat? Automaticky retry s exponential backoff. Po N pokusech → dead-letter topic. Nic se neztrati.
Klicovy insight: Pulsar ma Kafka protocol handler (KoP). To znamena, ze existujici Kafka klienti se pripojej k Pulsaru bez jedine zmeny kodu. Nulovy vendor lock-in.

Cilova architektura

IM 4.0 — Event-Driven s Apache Pulsar

Zmeny v IM

Co se zmeni v .NET kodu — minimalne

PRED (API odpovida)
  • IM ceka na dotazy od konzumentu
  • Odpovida na GET requesty: /api/stock, /api/products
  • Kazdy konzument = novy API projekt v IM
  • Konzument musi vedet, ze se neco zmenilo (nevi — tak polluje)
  • Push je "fire and forget" — bez zaruky doruceni
PO (IM publikuje)
  • IM detekuje zmenu → publish event do Pulsar
  • Konzumenti si subscribujou sami
  • IM NEVI, kdo cte. A nemusel by to vedet.
  • Novy konzument = 0 zmen v IM
  • Doruceni garantovano Pulsarem (persistent + DLQ)
// Kdyz se zmeni sklad v ERP:
await producer.Send(new StockChangedEvent {
    ProductId = "SKU-12345",
    Quantity = 42,
    Warehouse = "CZ-HLAVNI",
    Timestamp = DateTime.UtcNow
});
// Hotovo. E-shop, POS, Akeneo... vsichni dostanou event automaticky.
Klicove: IM zustava .NET modularni monolit. Prida se jen DotPulsar NuGet balicek. MediatR handlery publikujou eventy misto cekani na poll. Zadne prepisovani, zadna nova architektura IM samotneho.

Zmeny u konzumentu

Konzumenti: subscribe misto poll

Co se konkretne zmeni pro kazdyho konzumenta? Tady je prehled — z pohledu konzumenta je to jednodussi nez dneska:

Konzument PRED (dnes) PO (Pulsar)
E-shop (PHP) Cron co 5 min → GET /api/stock Subscribe sconto.bridge.stock → process
POS Cron → GET /api/products Subscribe topic → auto-update
Analytics / BI Cron → GET /api/orders Subscribe → real-time dashboard
Moeve IM push (data loss risk) Subscribe → guaranteed delivery
Balikobot / Rottr Primo zapis do DB (live) Publish events → subscribe shipments topic
Novy system Novy API projekt v IM (tydny) Subscribe na topic (hodiny)
Tl;dr: Pridani noveho konzumenta = 0 zmen v IM. Proste se subscribne na topic a cte zpravy. To je cely trik.

Bonus: CDC

Debezium — automaticke eventy z PostgreSQL

IM ma vlastni PostgreSQL databazi (EF Core Code-First). Debezium umi cist WAL (Write-Ahead Log) a automaticky generovat eventy pro KAZDOU zmenu v DB. Bez jedineho radku kodu.

Co to znamena: IM nemusel explicitne publikovat eventy. Debezium zachyti KAZDY INSERT/UPDATE/DELETE automaticky z PostgreSQL WAL a posle ho do Pulsar topicu. Zero-code eventy. Proste to funguje.
Pozor: Vyzaduje wal_level = logical na PostgreSQL. Overit s DevOps (Alef). Neni to slozite, ale musi se to zapnout explicitne.

Jak se tam dostaneme

IM 2.0 → 3.0 → 4.0 — nic se nerozbije

Nepujdeme na to hurr. Kazdou fazi jedeme PARALELNE se starym systemem. Kdykoliv se muze rollbacknout zpet.

✓
IM 1.0 → 2.0: Monolit → 4 casti + Aurora HOTOVO
Uz mame za sebou. Monolit rozsekan na 4 samostatne nasaditelne casti. Migrace z MS SQL na AWS Aurora (PostgreSQL). Solidni zaklad pro dalsi kroky.
1
IM 3.0: Azure PG replika + IM = SSOT DALSI ETAPA
Zaklad vsech zmen. IM prestane cist data z CSV (Moeve) a zacne cist primo z Azure PostgreSQL repliky. Zakaznici, firmy, produkty, sklady — vsechno z PG repliky misto CSV. Zaroven: prepocty (ceny, dostupnost atd.) se presunuji z e-shopu DO IM. IM se stava Single Source of Truth. E-shop i POS konzumujou hotova data = neni treba replikovat logiku e-shopu do POS.
2
IM 4.0a: Pulsar PoC + prvni topic
Rozjet Apache Pulsar (StreamNative Serverless nebo self-managed na EKS). IM zacne publikovat stock changes do topicu sconto.bridge.stock. E-shop se subscribne. Crony bezej PARALELNE — kdyz Pulsar funguje, cron se nevyuzije (ale bezi pro jistotu). Overime latenci, spolehlivost, monitoring.
3
IM 4.0b: Rozsireni topicu
Pridame topicy: products, prices, orders, customers, shipments. Postupne migrujeme konzumenty na Pulsar. POS, Akeneo, Analytics, Moeve... kazdeho jednoho. Crony postupne vypiname — ale az kdyz jsme si jisti, ze Pulsar dorucuje spolehlive.
4
IM 4.0c: Full event-driven + Debezium
Vsechny integrace jedou pres Pulsar. Debezium CDC z IM PostgreSQL — automaticke eventy bez kodu. Crony ZRUSENY. IM = event producer only. Novy konzument = subscribe na topic. Hotovo za hodiny, ne tydny. Schema registry validuje vsechny zpravy. Tiered storage do S3 pro historii.
Bezpecnost: V kazde fazi lze ROLLBACK zpet. Stary system bezi paralelne. Faze 1 = CSV jako fallback. Faze 2-4 = crony jako fallback. Zadne "vse nebo nic" risiko.
Znamy bottleneck: Moeve ERP webservice — jedina API trubka do ERP. Bezi 3 roky v kuse na Windows serveru. Nikdo na to nesaha, vsichni se toho boji. V ramci IM 3.0 (PG replika) tento bottleneck OBEJDEME — cteme primo z repliky, ne pres webservice. Ale dlouhodobe si na to musime nekdy kouknout.

FAQ

Caste otazky

Proc ne SQS/SNS?
AWS-native, ale: zadny replay historickych zprav, zadna schema registry, vendor lock-in na AWS. Pulsar = open-source, cross-cloud, provozovatelny kdekoliv. A ma Kafka protocol handler, takze zero lock-in.
Proc ne Kafka?
Kafka je skvele. Ale: broker = storage (skalovani = rebalancing, coz je bolestive). Max tisice topicu na cluster (Pulsar = miliony). Zadny individual ack na zpravy. Zadny built-in multi-tenancy. Pulsar tohle vsechno resi nativne.
Musime prepsat IM?
NE. IM zustava .NET modularni monolit. Prida se DotPulsar (NuGet balicek). MediatR handlery publikujou eventy. Minimalni zmena v existujicim kodu. Zadne prepisovani, zadna nova architektura.
Co kdyz Pulsar spadne?
Persistent topics = data na disku (BookKeeper, 3 repliky). Tiered storage do S3 = dalsi vrstva bezpeci. Nic se neztrati. A StreamNative (managed) ma 99.95% SLA. Spolehlivejsi nez nase soucasne "fire and forget" pushe.
Kdo to bude spravovat?
StreamNative = plne managed, zero-ops. Self-managed = DevOps (Alef) + Helm chart na EKS. Oba modely fungujou. Doporucujeme zacit managed, aby se tym mohl soustredit na business logiku, ne na infrastrukturu.
Jde to kombinovat s PHP microservices?
ANO! PHP Symfony Messenger → SQS transport → Pulsar SQS connector. Nebo primo Pulsar PHP klient. Nebo pres KoP (Kafka protocol) — kazdy Kafka PHP klient se pripoji na Pulsar. Nulove omezeni jazyka.
A co ten Moeve webservice?
Znamy bottleneck: jedina API trubka do ERP Moeve bezi 3 roky v kuse na Windows serveru. Nikdo na to nesaha, vsichni se toho boji. IM 3.0 (PG replika) tento bottleneck OBCHAZI — cteme primo z repliky DB. Ale dlouhodobe si na to musime kouknout a zmodernizovat.
