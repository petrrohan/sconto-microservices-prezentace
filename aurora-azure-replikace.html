A
Nativni PG replikace
Jak: PostgreSQL Publication/Subscription. Aurora publikuje WAL, Azure PG subscribuje.

+ Nejnizsi latence (<1s)
+ Zadne dalsi naklady (nativni PG)
+ Jednoduchy setup (jen SQL)

– Aurora failover = ztrata slotu
– DDL zmeny rucne
– Monitoring = nase starost
$50–150/mes
B
AWS DMS
Jak: AWS Database Migration Service. Full load + ongoing CDC. Managed instance v AWS.

+ Managed (AWS se stara)
+ Full load + CDC v jednom
+ Flat pricing (ne per-row)
+ Vestavena validace

– Aurora failover = restart tasku
– Problemy s JSONB/PostGIS
$200–400/mes

Airbyte (OSS)
Jak: Open-source ETL. Debezium pod kapotou. Jednoduche UI pro konfiguraci.

+ Nejjednodussi UI/setup
+ 300+ konektoru (budouci pouziti)
+ OSS verze zdarma

– Micro-batch (min ~1–5 min)
– Vyssi latence nez A/B
– Infrastruktura na nas
$200–500/mes

AWS DMS — nejlepsi pomer jednoduchost / vykon

DOPORUCENO
Scenar B: AWS DMS
Aurora PG (wal_level=logical)
  → AWS DMS (full load + ongoing CDC)
    → Azure PostgreSQL (Flexible Server)
      → dbt (transformace do analytickych modelu)
  • Managed = AWS se stara o infrastrukturu
  • Flat pricing = $200–400/mes nezavisle na objemu
  • Full load + CDC v jednom nastroji
  • Vestavena validace source vs. target
  • CloudWatch monitoring z boxu
  • Sekundova latence (near real-time)
Fallback plan
Kdyz DMS nestaci (datove typy, latence, slozitost):
  • Eskalace na nativni PG replikaci — nizsi latence, zadne naklady navic, ale vic ops prace
  • Nebo Airbyte OSS — kdyz potrebujeme vice zdroju dat (ne jen Aurora)
Prerequisity
  • rds.logical_replication = 1 na Aurora (reboot!)
  • Cross-cloud sit: VPN nebo public endpoint + TLS
  • Tabulky musi mit PRIMARY KEY
  • DDL zmeny rucne na obou stranach (Flyway/Liquibase)

Pozor na

Kriticke gotchas — at nas to neprekvapl

1
Aurora failover = ztrata slotu
Pri Aurora failoveru (writer → reader promotion) se replication sloty ZTRATI. DMS task se musi restartovat, mozny re-sync. Musi byt automation + CloudWatch alarm na OldestReplicationSlotLag.
2
Neaktivni slot = zaplneny disk
Kdyz subscriber spadne a slot zustane, WAL soubory se hromadi a MUZE SE ZAPLNIT DISK. Nastavit max_slot_wal_keep_size jako safety net. CloudWatch alarm na TransactionLogsDiskUsage.
3
DDL zmeny se NEREPLIKUJI
Zadny CDC pristup automaticky nereplikuje CREATE/ALTER TABLE. Schema zmeny musime aplikovat rucne na obou stranach. Reseni: Flyway nebo Liquibase (schema migration tool).
4
Cross-cloud sit + WAL overhead
wal_level=logical = +10–20% vic WAL dat (vyssi I/O). Cross-cloud latence = VPN ($) nebo public endpoint s TLS. Egress z AWS = ~$0.09/GB. Overit s Alefem (DevOps).
Dobra zprava: Vsechny tyto gotchas jsou resitelne. DMS ma built-in recovery pro failover. Monitoring pres CloudWatch existuje. Schema migrace pres Flyway je standard. Nic z toho neni showstopper.

  • Full load + prepnout na ongoing CDC
  • Nastavit monitoring (CloudWatch alarmy)
